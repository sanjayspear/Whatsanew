## ROLE
Act as a Principal Mobile Architect + AI Systems Engineer. You are designing and

## NORTH STAR
Build a mobile-first, AI-first classifieds & discovery app for "what's happening

differentiator is that **the UI itself is generated by AI from user intent**,
not hardcoded screens. Users speak, type, or point a camera, and the app paints
a cinematic, personalized surface on the fly.

## 1. TECHNICAL STACK (NON-NEGOTIABLE)

- **Client**: Kotlin Multiplatform (KMP) targeting Android + iOS.
  - UI: Compose Multiplatform (Android + iOS)
  - Shared: Ktor client, SQLDelight, Koin, kotlinx.serialization, Coroutines/Flow
- **On-Device AI**: 
  - Text/Intent: Gemini Nano via Android AICore (Android), Core ML / Apple
    Foundation Models fallback (iOS). Cross-platform fallback: **Gemma 2B /
    Phi-3-mini INT4 via MediaPipe LLM Inference** or **llama.cpp (KMP bindings)**.
  - Vision: MediaPipe Tasks (image/video frame decode, object detection, OCR)
  - Speech: Android SpeechRecognizer + iOS Speech framework, wrapped in KMP
    `expect/actual`, with on-device Whisper.cpp (tiny/base) as offline fallback.
  - Recommend the best distilled model per platform with a decision matrix
    (size, latency, RAM, thermals, quality).
- **Server**: Kotlin + Spring Boot 3.x, microservices, deployed to Kubernetes.
  - Service mesh ready, gRPC between services, REST/GraphQL at edge.
  - Kafka (or NATS) for event streaming between mobile ingestion and AI server.
  - PostgreSQL + pgvector for embeddings, Redis for session cache, S3 for media.
- **AI Server**: Separate inference + training stack (Python FastAPI or Triton)
  that Spring Boot services call. Includes: personalization engine, embedding
  store, recommendation ranker, distillation pipeline (LoRA fine-tune → quantize
  → export to Core ML / TFLite / GGUF → ship to devices).

## 2. CORE PRODUCT BEHAVIOR

### 2.1 Entry Experience
- Landing screen has two primary buttons: **"What's New"** and **"Legacy"**.
- Each button is text-labeled but visually dominated by a **slowly rotating,
  translucent 3D geometric solid** rendered in real time (choose the best fit
  from: Tetrahedron, Cuboctahedron, Rhombicosidodecahedron, Great Icosahedron —
  justify your pick for visual weight, GPU cost on mid-tier phones, and how it
  complements a glassmorphism/neumorphism card system).
- Render with **Filament (Android) + Metal/SceneKit (iOS)** via KMP expect/actual,
  OR a Compose-canvas + OpenGL/Skia shader path — pick one and justify.

### 2.2 Intent-Driven Dynamic UI (THE CORE FEATURE)
- User inputs intent via **any modality**: text, voice, camera snapshot, short
  video, or a mix. Examples:
  - "Show me new cafes in Koramangala within 3 km"
  - "Any drama or theatre near Ravindra Kalakshetra this weekend?"
  - "Change my app theme to something warm and quieter."
  - "Move the map to the top of the screen."
- The **on-device distilled model** parses intent → emits a **UI Intent DSL**
  (JSON schema you define), which a **Compose Multiplatform renderer** consumes
  to dynamically compose the screen from a **component registry** (cards, maps,
  video tiles, carousels, CTA buttons, contact sheets, etc.).
- NO text-chat response. Output is always **cinematic surfaces**: cards, maps,
  embossed/glass panels, video players, call buttons, booking sheets.
- UI DSL must support: theme mutations (color, elevation, blur, radius,
  typography scale), layout reordering, component insertion/removal, and
  personalized ranking of list items.

### 2.3 Visual Language
- **Not Material Design cards.** A unified system of:
  - Neumorphic (soft-embossed) surfaces for primary actions
  - Glassmorphic (blurred translucency) panels for overlays and media
  - Consistent radius, shadow, and tint scales tied to the geometric motif
  - Reference feel: cinematic, spatial, layered — think Apple Sports + Arc
    Search + a boutique hotel booking app.
- Every card is **interactive and actionable**: plays inline YouTube, opens
  Maps, deep-links to dialer, opens event booking, saves to a personal shelf.

### 2.4 Personalization & Learning Loop
- On-device: user interaction signals (taps, dwell, dismissals, explicit likes,
  search refinements) are logged locally and used to re-rank locally.
- Periodically (batched, differential-privacy-respecting) upload signals to the
  AI server via the Spring Boot ingestion service.
- AI server aggregates across users → retrains personalization + ranking models
  → produces a **new distilled model** → devices pull via OTA-style model
  versioning (signed, delta-updated).
- Example behavior: user attended a drama at Ravindra Kalakshetra in Feb and
  liked it → the system should surface similar theatre, drama festivals, cinema
  in that genre, and nearby venues.

### 2.5 Offline-First
- Full intent parsing, UI generation, and cached-content browsing must work
  **with zero network**. Transcription, voice, image, and video-frame
  understanding run on-device. Server is an enhancer, not a dependency.

### 2.6 Scale Roadmap
- Phase 1: Bangalore. Phase 2: Tier-1 India. Phase 3: Global.
- Data models, locale handling, currency, and geo indexing must be **global-ready
  from day one**, even if only Bangalore data is seeded.

and a JUnit 5 test skeleton.

- **Do NOT** propose a ChatGPT-wrapper UX. No chat bubbles. No wall of text.
- **Do NOT** hardcode screens. Every non-landing surface must be
  dynamically composable from the UI DSL.
- **Do NOT** make the server a hard dependency for core UX.
- Prefer **boring, proven technology** over bleeding edge unless justified.
- Every architectural choice must survive: 10x users, 10x content types,
  10x locales, 5+ years of feature accretion.
- Assume mid-tier Android (Snapdragon 7-series, 6 GB RAM) is the perf floor.
